`macos-appkit` is a Tier 1 target for desktop apps. Day creates AppKit controls from Rust
through its AppKit toolkit. Use it when your app needs a Mac interface alongside the code
you share with other targets.

## Getting started

Install **full Xcode 27 or newer**. The macOS host uses the JSON5 `project.xcproj`
format and builds through `xcodebuild`; command-line tools alone are insufficient.

```sh
sudo xcode-select -s /Applications/Xcode.app
cargo install --git https://github.com/daybrite/day day-cli
day new app my-app --toolkit macos-appkit
cd my-app
day launch -t macos-appkit
```

`day doctor --toolkit appkit` turns the AppKit checks into errors and prints setup help for
anything missing. Packaging produces a `.dmg`:

```sh
day pack -t macos-appkit            # without signing config: ad-hoc codesign, marked dev-signed
day pack -t macos-appkit --formats dmg
```

Signing and notarization happen when the credentials are configured; see
[packaging](/docs/how-to/packaging). Without them, `day pack` ad-hoc codesigns and warns that the result
is dev-signed: installable locally, and not for distribution. `--no-sign` is the only way to get
an artifact with no signature at all.

When a dependency contributes Swift under `[package.metadata.day.macos]` (the
[SwiftUI embedding](/docs/reference/swiftui) shim, or an app's own local SwiftPM package),
`day build` generates a `DayPieces` SwiftPM package under `build/day/macos/`. An app carrying
the generated `build/day/xcode/macos/DayApp.xcodeproj` (or a checked-in override) builds through xcodebuild, which references that
package; on the bare-cargo path (`DAY_MACOS_XCODE=0`, or no scaffold) `day build` runs
`swift build` and statically links the result into the cargo binary. An app with no Swift
contributions needs no Swift toolchain either way.

## Caveats

- `day launch` runs a bare binary, not a bundle. Anything the OS gates on bundle identity
  (TCC permission prompts, some system services) only works from `day pack` output. Develop with
  [`launch`](https://daybrite.dev/api/day/fn.launch.html), and verify permission flows against a packed build.
- `day-piece-lottie` ships UIKit and Android arms only.
- Pull-to-refresh is emulated: the piece observes [`NSScrollView`](https://developer.apple.com/documentation/appkit/nsscrollview)'s elastic overscroll,
  because macOS has no native refresh control.
- Screenshots capture offscreen (`cacheDisplayInRect:`), which cannot sample video layers or
  [`NSVisualEffectView`](https://developer.apple.com/documentation/appkit/nsvisualeffectview) materials, so an [`AVPlayerView`](https://developer.apple.com/documentation/avkit/avplayerview) comes out black in `day pack` captures and
  in the gallery. The view itself renders correctly on screen.

[`toggle`](https://daybrite.dev/api/day_pieces/fn.toggle.html) is the only boolean control, radio behavior is [`picker`](https://daybrite.dev/api/day_pieces/fn.picker.html)`()`[`.inline`](https://daybrite.dev/api/day_pieces/trait.PickerBuilder.html#tymethod.inline)`()`, and [`list`](https://daybrite.dev/api/day_pieces/fn.list.html) is the only
collection; there is no checkbox, stepper, or table piece. See [pieces](/docs/explanation/pieces) for the full
vocabulary.

**Text measurement** goes through AppKit itself (`cellSizeForBounds:` for labels, TextKit's layout
manager for the text area, and `fittingSize` for everything else), so wrapping and hyphenation are
the system's text layout.

## Reaching AppKit directly

When you need something Day doesn't model, a [tweak](/docs/how-to/tweaks) hands you the realized [`NSView`](https://developer.apple.com/documentation/appkit/nsview)
for a node, so you can set any AppKit property.
