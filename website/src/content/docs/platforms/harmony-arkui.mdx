`harmony-arkui` is a Tier 3 experimental target. Day uses ArkUI’s native node API with an
ArkTS host project. Evaluate the controls and services your app needs before choosing it for
distribution; a local compile check does not establish device or store readiness.

## Getting started

This toolchain takes the most setup steps of any Day supports. You need
[`cargo-ohos`](https://crates.io/crates/cargo-ohos), which downloads the OpenHarmony SDK and
drives the cross-compile, plus the command-line tools (hvigor, `hdc`, the signing tools);
`day doctor --toolkit harmonyos` checks each piece and prints setup help, and the
[HarmonyOS notes](/docs/how-to/harmonyos) cover the install in detail.

```sh
cargo install --git https://github.com/daybrite/day day-cli
cargo install --locked cargo-ohos
cargo ohos init sdk --api 18
day new app my-app --toolkit harmony-arkui
cd my-app
day build -t harmony-arkui       # cross-compiles, then hvigor → signed .hap
day launch -t harmony-arkui      # installs and starts on an emulator or device
```

`day build` signs the `.hap` with the public development certificate, so you get an installable
artifact without a vendor account. `day pack -t harmony-arkui` produces the release `.hap`, signed
with your own material when configured.

The [`day devices boot`](/docs/reference/cli#simulators-emulators-and-devices) command starts the emulator: `day devices boot -t harmony-arkui` (add
`--headless` to run without a window) boots the emulator image under QEMU and connects `hdc`:
Oniro's for OpenHarmony 6.x, or harmony-contrib/ohos-qemu's `x86_64_virt` for 7.0, recognized by
its files. It does not download images: unpack the Oniro release's `oniro_emulator.zip` into
`~/ohos/emulator`, or point `DAY_OHOS_EMULATOR` at either image's `images/` directory; otherwise
the command errors naming what is missing.
[System requirements](/docs/reference/system-requirements#setting-up-the-oniro-emulator) has the download, the
QEMU install, and KVM setup.

Day derives the hvigor project under `build/day/harmony/project/`; no checked-in build
scaffold is required. `day open -t harmony-arkui` prepares and opens it in DevEco Studio.
For custom native configuration, `day project add-target harmony-arkui --persist-native-project`
creates an editable `platform/harmony/` override. Day stages that override for builds,
so edit its source files rather than the disposable project under `build/`.

## Caveats

The widget vocabulary is implemented; platform integration is partial:

- [`present()`](https://daybrite.dev/api/day_core/fn.present.html) handles file open/save; alerts and prompts are ignored. If your UI depends on a
  confirmation dialog, it will silently do nothing here.
- Several external pieces have no ArkUI arm: media, map, Lottie, search field, combo box,
  activity indicator, and remote image all render a placeholder. The date/time pickers and
  pull-to-refresh have native arms, and the web view has an **ArkTS** arm: the crate ships its own
  ArkTS component, staged into the host project via `[package.metadata.day.ohos]`, with load,
  back/forward, stop, and reload working.
- Animation ([`with_animation`](https://daybrite.dev/api/day_core/fn.with_animation.html), [`.animation`](https://daybrite.dev/api/day_pieces/trait.Decorate.html#method.animation)) runs on ArkUI's own animator (`animateTo`):
  opacity, transform, and background color interpolate with the requested curve, duration,
  delay, and repeat, and a spring follows Day's own spring curve. Frame changes (layout moves
  and resizes) apply instantly, as on Android.
- All three picker styles collapse to one control: menu, segmented, and inline all become
  [`ARKUI_NODE_TEXT_PICKER`](https://github.com/openharmony/docs/blob/master/en/application-dev/reference/apis-arkui/capi-native-node-h.md).
- Layout is measured for very few kinds. Labels, buttons and the text area ask ArkUI to measure;
  nearly everything else uses a fixed size, so unusual content may not fit as it does on other
  targets.
- Much of the platform requires ArkTS, reached through the host project because the C API
  does not expose it: navigation (`Navigation`/`NavPathStack`), file pickers, opening a URL,
  bundled resources, custom font registration, and app bootstrap. Day wires all of this in the
  scaffold; you meet the ArkTS side when you go past what Day models.
- Emulator behavior in CI is tolerated-flaky; the build and packaging steps gate hard.

## What each piece becomes

The generated [coverage matrix](/contributing/backend-contracts/coverage-matrix), checked in CI, covers every toolkit;
this table adds links and notes.

Day calls the ArkUI native node API directly, so the mapping below is in terms of `ArkUI_NodeType`
values. Where HarmonyOS's [NDK development guides](https://developer.huawei.com/consumer/en/doc/harmonyos-guides/arkts-use-ndk)
cover a component, the node type links to that guide; the rest link to the OpenHarmony
`ArkUI_NodeType` reference.
